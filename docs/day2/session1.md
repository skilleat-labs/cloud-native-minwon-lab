# Day 2 · 1차시 — 수정 버전이 나왔는데 서버마다 환경이 다르다

**소요 시간**: 50분 (10:00~10:50)
**목표**: VM 배포 방식의 한계를 이해하고, 컨테이너와 이미지의 개념을 파악한다

---

## 학습 목표

이 차시를 마치면 다음을 할 수 있습니다.

- VM 직접 설치 방식이 왜 서버마다 결과가 달라지는지 설명할 수 있다
- 컨테이너와 이미지의 관계를 VM과 비교해 설명할 수 있다
- 레지스트리(NCR)가 어떤 역할을 하는지 설명할 수 있다

---

## 개념 — 어제 방식의 한계

### 수정 버전을 배포하면 생기는 일

| STEP | 내용 |
|------|------|
| STEP 01 | 서버 접속 — SSH로 한 대씩 |
| STEP 02 | 기존 서비스 중지 — 잠깐 멈춤 |
| STEP 03 | 새 파일 교체 — 수동 또는 스크립트 |
| STEP 04 | 설정 조정 — 서버마다 다를 수 있음 |
| STEP 05 | 재시작, 확인 — 한 대씩 반복 |

### 여기서 생기는 문제들

| 문제 | 왜 생기는가 |
|------|-----------|
| 서버마다 결과가 다르다 | OS 패치 수준, 라이브러리 버전, 설정 파일이 조금씩 다름 |
| 배포 시간이 서버 수에 비례한다 | 한 대씩 접속해서 같은 작업을 반복해야 함 |
| 배포 중 서비스가 끊긴다 | 중지 → 교체 → 재시작 사이에 요청을 받을 수 없음 |
| 되돌리기가 어렵다 | 이전 상태가 어떤 모습이었는지 정확히 기록되어 있지 않음 |
| 서버가 죽으면 사람이 알아채야 한다 | 자동으로 다시 살려 주는 장치가 없음 |

!!! warning "핵심"
    "내 서버에선 되는데요"라는 말이 나오는 순간, 실행 환경이 통제되고 있지 않다는 뜻.

## 개념 — 컨테이너란 무엇인가

### VM vs 컨테이너

```
가상 머신 (VM)                       컨테이너
┌────────┬────────┐           ┌────────┬────────┬────────┐
│ 앱 A   │ 앱 B   │           │ 앱 A   │ 앱 B   │ 앱 C   │
├────────┼────────┤           ├────────────────────────────┤
│게스트OS│게스트OS│           │      컨테이너 런타임       │
├────────────────┤           ├────────────────────────────┤
│   하이퍼바이저  │           │    호스트 OS 커널 (공유)    │
├────────────────┤           ├────────────────────────────┤
│    호스트 OS    │           │          하드웨어           │
└────────────────┘           └────────────────────────────┘
```

| 비교 항목 | 가상 머신 | 컨테이너 |
|---------|---------|---------|
| 포함하는 것 | 게스트 OS 전체 + 앱 | 앱 + 필요한 라이브러리 |
| 시작 속도 | 운영체제 부팅 시간 필요 | 프로세스 실행 수준으로 빠름 |
| 크기 | 수 GB | 수십~수백 MB |

## 개념 — 이미지와 컨테이너

### 붕어빵 틀(이미지)과 붕어빵(컨테이너)

```
이미지 (Image)
실행에 필요한 모든 것을 담은 읽기 전용 패키지
            ↓        ↓        ↓
     [컨테이너 1] [컨테이너 2] [컨테이너 3]
     하나의 이미지로 몇 개든 똑같이 만들 수 있음
```

| 개념 | 설명 |
|------|------|
| 이미지 | 변하지 않는 읽기 전용 패키지. 같은 이미지는 어디서나 같은 내용 |
| 컨테이너 | 이미지를 실행한 상태. 실행 중 생긴 변경은 그 컨테이너 안에만 남음 |
| 태그 | 이미지의 버전을 식별하는 라벨 (예: `complaint-app:1.0`) |

!!! tip "어제와 달라지는 점"
    어제: "서버에 들어가서 파일을 바꿨습니다"
    오늘부터: "새 이미지로 컨테이너를 교체합니다"

### 이미지 레이어 구조

```
민원 서비스 애플리케이션 파일     ← 최상위 (가장 자주 바뀜)
애플리케이션 의존 라이브러리
런타임 (Python 3.11)
기본 OS 파일 시스템 (베이스 이미지) ← 최하위 (거의 안 바뀜)
```

바뀐 층만 전송되므로 새 버전 배포가 가볍고 빠릅니다.

## 개념 — 레지스트리

### 이미지 흐름

```
이미지 빌드 → Push → [레지스트리] → Pull → 컨테이너 실행
```

레지스트리는 이미지를 보관하고 필요한 곳에 내려주는 저장소입니다. **NHN Container Registry(NCR)** 가 이 역할을 합니다.

---

## STEP 01 — NCR 서비스 활성화

```
상단 메뉴 > 서비스 선택 > Containers > NHN Container Registry(NCR) > 서비스 활성화
```

---

## STEP 02 — 레지스트리 생성

### 콘솔 경로

```
Containers > NHN Container Registry(NCR) > 레지스트리 생성
```

### 설정값

| 항목 | 값 |
|------|---|
| 이름 | `minwon-registry` |
| 접근 정책 | Private |
| 이미지 정리 정책 | 사용 안 함 |

---

## STEP 03 — 레지스트리 접근 정보 확인

레지스트리를 생성하면 **이미지를 Push/Pull할 주소**가 생깁니다.

```
Containers > NCR > [minwon-registry] > 기본 정보
→ 레지스트리 주소 확인 (예: {리전}.registry.container.nhncloud.com/{레지스트리명})
```

| 항목 | 내가 확인한 값 |
|------|-------------|
| 레지스트리 주소 | |

---

## STEP 04 — 이미지 확인

이 실습에서는 강사가 미리 빌드해 둔 이미지를 사용합니다.

!!! info "이미지 빌드는 이 과정에서 다루지 않습니다"
    컨테이너 이미지 빌드(Dockerfile 작성, docker build)는 이번 과정의 범위 밖입니다.
    빌드가 완료된 민원 서비스 이미지가 강사 레지스트리에 준비되어 있습니다.

강사에게 아래 정보를 받아 기록합니다.

| 항목 | 값 |
|------|---|
| 이미지 주소 | `{레지스트리 주소}/complaint-app:latest` |

## 1일차 개념과 오늘 개념 비교

| 1일차 (VM 방식) | 2일차 (컨테이너 방식) | 무엇이 좋아졌나 |
|---------------|---------------------|--------------|
